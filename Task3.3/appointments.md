# API для мобильного приложения (OpenAPI)

По заданию был реализован HTTP endpoint `/appointments`.
Спецификация OpenAPI 3.2.0 приведена [в файле](./OpenAPI_appointments.yaml).

## Комментарий к спецификации

### Версионирование

Выбрано версионирование через URL (`/api/v1/appointments`).

Это простой и наглядный подход: клиент (Мобильное приложение) явно знает, с какой версией работает, а API Gateway легко маршрутизирует запросы.

При появлении несовместимых изменений (например, удаление поля) выпускается новая версия `/api/v2/...`, а старая поддерживается в течение переходного периода (например, 3 месяца или пары спринтов).

### Пагинация

Выбрана пагинация через `limit` и `offset`. Для списка записей пациента это оптимальный выбор:

- данных немного (десятки записей), поэтому производительность не страдает
- клиенту нужна возможность перейти на произвольную страницу (например, "показать ещё 10")
- курсорная пагинация здесь избыточна: она нужна для больших или динамичных наборов данных (например, ленты событий).

Если в будущем количество записей вырастет (например, добавятся архивные записи за годы), можно перейти на курсорную пагинацию (`cursor` / `next_cursor`).

### Фильтрация

Мобильное приложение может показать пациенту разные экраны: "Предстоящие", "История посещений", "Отменённые записи". Поэтому логичнее в параметры фильтрации добавить такой enum. Это будет сделано в рамках одного эндпоинта, а не нескольких отдельных.

Эндпоинт поддерживает фильтрацию по параметру `status`:

- `upcoming` — предстоящие записи (по умолчанию)
- `completed` — завершённые записи (история)
- `cancelled` — отменённые записи.

Если параметр не указан, то возвращаются только `upcoming` (по умолчанию). Если параметр указан, то фильтр применяется на стороне CRM.

Фильтрация комбинируется с пагинацией и можно запросить `status=completed&limit=10&offset=0`.

### Аутентификация

Используется **JWT (Bearer token)**. Пациент аутентифицируется через мобильное приложение (OIDC/JWT). API Gateway проверяет токен и передаёт `patient_id` в CRM. Пациент видит только свои записи (tenant-scoped доступ).

Работу с OIDC/JWT можно проводить через Keycloak или аналог. Разобрать и провалидировать JWT может и сам API Gateway.

### Коды ответов

Для списка записей (`GET /appointments`):

- `200 OK` — успешный ответ со списком записей
- `401 Unauthorized` — токен отсутствует или недействителен
- `422 Unprocessable Entity` — если параметры фильтрации некорректны (например, limit=1000).
- `500 Internal Server Error` — внутренняя ошибка сервера.

Дополнительно возможно добавить:

- `403 Forbidden` — если пациент пытается получить записи другого пациента (tenant-scoped доступ).  
  Это возможно, если добавится эндпоинт `/appointments/{id}` 
  (получение деталей одной записи). Для списка записей 403 не возникает, 
  потому что пациент видит только свои записи (фильтрация по `patient_id` 
  из JWT-токена).
