# Анализ текущей интеграционной архитектуры

## Цель документа

В данном документе выявлены системные проблемы текущего ИТ-ландшафта "Здоровья+", которые создают риски для запуска мобильного приложения. Проблемы сгруппированы по архитектурным слоям и подтверждаются артефактами из Jira, Service Desk, отзывов сотрудников и новостей.

## Таблица проблем

| ## | Проблема | Признаки | Влияние на приложение |
| -- | -- | -- | -- |
| 1 | Отсутствие гарантий доставки в критичных интеграциях | **INT-001**: при таймауте деньги списываются, статус не фиксируется<br>**SD-002**: "Booking not found" для paymentID<br>**SD-009**: двойное списание денег<br>**INT-002**: FTP падает, данные теряются до следующего дня<br>**INT-011**: CRM не обновляется после передачи из LIS | Потеря денег пациентов, двойные записи, некорректные статусы в приложении, пользователь будет видеть "Оплачено", а записи нет |
| 2 | Отсутствие идемпотентности в операциях записи | **INT-005**: дубли записей при повторных POST<br>**SD-003**: двойная запись на один слот<br>**Дмитрий (Техлид расписания)**: "не умеем различать повторные запросы" | Приложение будет создавать дубли при плохом интернете (повторная отправка создает ещё одну сущность) |
| 3 | Каскадные сбои из-за синхронных цепочек без защиты | **INT-003**: 1С падает при >50 rps<br>**SD-001**: 1С отвечает >30 секунд<br>**SD-008**: полис недействителен (1С вернул null)<br>**Алексей (разработчик)**: "1С внезапно меняет контракт, rate limiting нет" | Мобильное приложение будет зависать при проверке полиса или оплате. Пользователь не сможет завершить сценарий |
| 4 | Перегрузка брокера сообщений (RabbitMQ) | **INT-004**: лимиты RabbitMQ не документированы<br>**SD-006**: пуши не приходят из-за переполнения<br>**INT-007**: отсутствие distributed tracing<br>**Елена (DevOps)**: "очередь упала с ошибкой 404" | Уведомления о записи и готовности анализов не будут доходить. Пользователь не узнает о статусе |
| 5 | Legacy-интеграции без автоматического восстановления | **INT-002**: FTP падает с ошибкой 425, ручное восстановление<br>**SD-005**: утром нет анализов в CRM (скрипт упал ночью)<br>**Алексей (разработчик)**: Perl-коннектор без документации и сопровождения | Результаты анализов не появятся в приложении вовремя. Пациент будет звонить в кол-центр, а цель наоборот снизить нагрузку на 30%, она не будет достигнута |
| 6 | Отсутствие изоляции и rate limiting для внешних систем | **INT-003**: 1С падает при >50 rps<br>**Алексей (разработчик)**: "при небольшом всплеске 1С перестаёт отвечать" | При росте пользователей приложения (MVP: 500, целевое: 50 000) мы положим 1С и платёжный шлюз |
| 7 | Проблемы безопасности | **INT-006**: SQL-инъекция в веб-портале<br>**SD-007**: врач видит чужого пациента (подмена сессии?) | Очень вероятна утечка персональных данных пациентов. Репутационные и юридические риски (152-ФЗ) |
| 8 | Отсутствие единой точки контроля | **INT-010**: эпик на разработку API Gateway<br>**INT-007**: нет distributed tracing | Невозможно централизованно управлять безопасностью, лимитами и мониторингом |
| 9 | Отсутствие управляемой интеграции с системами | Разные протоколы (REST, SOAP, FTP, 1С HTTP)<br>**Алексей (разработчик)**: "документации нет" | Каждый новый сценарий в приложении будет требовать новой интеграции, но нет описания ни текущих интеграций, и новые делать вносить проблематично |

## Вывод

Текущая архитектура не готова к запуску мобильного приложения. Основные риски:

1. **Потеря денег и данных** из-за отсутствия гарантий доставки.
2. **Дубли записей** из-за отсутствия идемпотентности.
3. **Каскадные сбои** из-за синхронных цепочек и отсутствия rate limiting.
4. **Перегрузка RabbitMQ** и отсутствие наблюдаемости.
5. **Уязвимости безопасности**.

Эти проблемы требуют системных архитектурных решений (API Gateway, идемпотентность, асинхронные интеграции, retry, circuit breaker), а не точечных багфиксов. Решение должно учитывать эти риски.
